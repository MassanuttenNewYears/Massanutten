# Knowledge Base

## Overview

`massanutten` is a static GitHub Pages site for the org `MassanuttenNewYears` (remote: `https://github.com/MassanuttenNewYears/Massanutten.git`, branch `main`). Invite-only trip site for New Years 2026 at Massanutten: a winter-themed login page gates a home page with the roster (names light up after each person's first sign-in) and the itinerary, loaded from Supabase. The Cars section is off the home page for now.

- **How to run:** serve the folder over HTTP (e.g. `python3 -m http.server`); ES modules do not work from `file://`. No build step. Deploy via GitHub Pages (Settings > Pages > `main` branch, root). Expected URL: `https://massanuttennewyears.github.io/Massanutten/`.

## Architecture

- `styles.css`: shared winter theme (night gradient, frosted `.card`, inputs/buttons, `.status`).
- `snow.js`: classic script on every page. Injects a fixed canvas drawn at 1/4 resolution, scaled with `image-rendering: pixelated` (square flakes, 3 depth layers, sine drift). Pauses when the tab is hidden; static under `prefers-reduced-motion`.
- `login.html` + `login.js`: login. Personal links `login.html#e=<login email>&k=<key>` are read from the fragment, the fragment is removed with `history.replaceState`, then `signInWithPassword` + `rpc('mark_first_sign_in')`, then redirect to `./`. Manual email/password form also calls the RPC. Bad link shows an error.
- `index.html` + `app.js`: home. `#app` stays hidden until `guard()` passes (session exists, younger than 8h, and `auth.getUser()` confirms it with the server); otherwise redirects to `./login.html`. Renders roster table (one column per `group_label`, groups in `people.id` order, rows by `sort_order`) and itinerary day cards. The Cars section is not rendered. The signed-in name in the header is a link to `account/` (site path `/Massanutten/account/` on GitHub Pages; no leading slash, so the project subpath is kept). Roster card headings only are remapped in `ROSTER_HEADINGS` (`Folk` → `MOIDS (FOLK)`, `Foids (W)` → `FOIDS (W (We <3 you Women))`); stored `group_label` is unchanged. Placeholder logins show as the slug in the header.
- `account/index.html` + `account/account.js`: account page for the signed-in user. Same auth gate, then `profiles` select (`id, display_name`) filtered to `auth.uid()`; `profiles_select_own` is the RLS enforcement (a row whose id is not the session user is refused). Password change is `auth.updateUser({ password })`, which updates only the token's user, then `mark_first_sign_in()`. The current password cannot be shown: Auth stores a hash, not the password. The page then calls `list_potential_drivers()`. On success it shows a Potential drivers table (names only; empty list says "None yet."). Any error leaves that section hidden. It also calls `my_secret_liquor()`. When that returns a name, a Secret liquor section shows "Your target is {name}." Otherwise that section stays hidden. The page has no admin label.
- **Bringing list** (right of the roster, `#bring-list`/`#bring-form` in `index.html`, logic in `app.js`): signed-in users add/edit/delete their own entries; everyone sees all. See "Bringing list" below.
- `supabaseClient.js`: single `createClient` (URL + publishable key, **sessionStorage** session), `SITE_URL`, and the forced re-login helpers `signIn` (stamps sign-in time), `sessionExpired`, `endSession`, `MAX_SESSION_MS` (8h).
- `supabase/migrations/*.sql`: idempotent copies of schema migrations applied via MCP (no secrets; account creation SQL is intentionally not saved).
- `invite.py` (gitignored): local invite mailer, see "Invites".
- `secret_liq.py` (gitignored): local secret-liquor draw, see "Secret liquor". The roster card border turns rainbow once every person has answered; see that section.
- `.cursor/mcp.json`: routes the `supabase` MCP server to this project (overrides global).

## Bringing list

- Why not a SHA-256 hash: a hash is one-way and cannot be "unhashed" for display. Instead entries are encrypted client-side with AES-256-GCM (key = PBKDF2-SHA256, 200k iterations, from a passphrase + a random 64-hex salt, both stored in `app_secrets`); stored value is base64(iv + ciphertext). The DB never sees plaintext.
- Tables (no API privileges at all; access only through security definer RPCs): `app_secrets` (`bring_passphrase`, `bring_salt`) and `bring_items` (person_id -> people, ciphertext must be base64, 40-1200 chars, enforced by `bring_items_ciphertext_format`; migration `20261012_bring_items_validate.sql`). RPCs, all `authenticated`-only: `get_bring_secret()` (returns passphrase + salt), `list_bring_items()` (id, person_name, ciphertext, created_at, mine), `add_bring_item(cipher)` (max 50 per person, needs a linked roster row), `update_bring_item(id, cipher)` / `delete_bring_item(id)` (own rows only). Migration: `supabase/migrations/20261012_bring_items.sql` (salt is generated when first applied; do not re-seed or old entries become unreadable).
- Threat model: outsiders (anon) cannot read ciphertext or the key. Any signed-in user can fetch the key (needed to decrypt), and anyone with DB/dashboard access can too, so this is obfuscation-at-rest, not secrecy from members. The passphrase is short, so it is mitigated only by the salt and by the key being sign-in-gated. Rotating the passphrase/salt requires re-encrypting all rows.
- **Layout:** the Bringing card is a separate right-hand column (`.layout` > `.main-col` [header, hero, all cards] + `aside.bring`, which starts at the top of the page) that is `position: sticky` so it follows the scroll (static on screens < 900px). The column is 400px so a name like "Katie M." fits on one line beside the shape and the edit/delete buttons. The page max-width is 1600px so the roster card is wide enough for its headings to stay on one line (`white-space: nowrap`). Entries render as a table: Shape, Name, Item, actions. Shape, name, and actions stay on one line; only the item text wraps.
- **Identity badges** (client-side only, computed in `computeIdentities()` from the `people` columns already fetched; no DB change): only people who RSVPed yes (`first_signed_in_at` set, not declined, not maybe) get one. They are ranked oldest-first by `first_signed_in_at` (order of RSVPing yes; John = triangle, Jack = square); rank 0 = triangle, shape = 3 + rank % 7 (triangle..nonagon, 7 shapes), color = rank % 2 (even = Maize & Blue `#FFCB05`/`#00274C`, odd = Scarlet/Gray/White `#BB0000`/`#8a8d8f`/white). Badges also appear next to names in the roster. Existing ranks only shift if someone before you switches to maybe/no. People without a yes show "-". Matching of entries to people is by `display_name`.
- Verified via rolled-back SQL tests (add/list/update/delete/get secret as John; 2026-10-12 role tests: `anon` is denied on both tables, `app_secrets`, and all 5 RPCs; `authenticated` is denied direct table access; Jack cannot edit or delete John's item). Advisors: only the expected INFO (RLS enabled, no policies = deny all) and WARN (signed-in-callable security definer RPCs, intentional). Not browser-tested.

## Accept / decline flow

- Email has two links to `invite.html#e=<login email>&k=<key>&a=accept|decline` (fragment is stripped on load; never sent to servers).
- Accept: sign in with the key, `accept_invite()` (clears `declined_at`), then the yes section: a "Can you drive?" subsection and the "Choose a password" form (min 6 chars client-side). Yes calls `offer_to_drive()` and adds that recipient to `potential_drivers`. No writes nothing. Saving the password calls `updateUser`, then `mark_first_sign_in()` (this is what triggers the rainbow name), then redirect home. Login alone no longer triggers the rainbow; saving a password on the account page does too (that is how John would light up).
- Decline: sign in with the key, show a big ASCII frown with a confirm button (mail scanners opening the link can't decline by themselves); confirm calls `decline_invite()` (sets `people.declined_at`) and signs out. The page offers "Actually, I'm coming" (re-signs in from in-memory creds, `accept_invite()`, then the password step). Home page draws a red X (`.declined` CSS) through declined names.
- **Maybe RSVP:** third email button (`a=maybe`). `invite.js` calls `maybe_invite()` (sets `people.maybe_at`, clears `declined_at`) and offers "I'm in" / "I can't make it". Display precedence on the roster: declined (red X) > maybe (name lowercased then first letter capitalized, whole name teeters via CSS `teeter`) > rainbow (set a password) > grey lowercase. `accept_invite`/`decline_invite` clear the other state. A key beside the roster (`#legend-list`, built by `renderLegend()` from sample names) explains the four looks: grey = hasn't answered yet, rainbow = coming, teetering = maybe, red X = can't come. Migration: `supabase/migrations/20261009_maybe_rsvp.sql`; `maybe_at` is in the column-level SELECT grant.
- Schema: `people.declined_at`; `decline_invite()` / `accept_invite()` are security definer, `authenticated` only, act on the caller's own row. Migration: `supabase/migrations/20261009_invite_responses.sql`.
- Once a person sets a password their key stops working, so old invite links fail with "can't be used any more." They sign in on the login page with the email address the invitation was sent to and the password they chose. `mark_first_sign_in()` switches the Auth login to that address when they save the password. The nine people who had already saved one were switched the same way after the first send.
- **Password length:** the invite and account password forms require 6-72 chars client-side. Supabase Auth enforces its own server-side minimum (default 6) under Dashboard > Authentication > Sign In / Providers > Email; keep it at 6 or higher (it can't be read or set via MCP, so confirm it in the dashboard). The current password cannot be read back.

## Secret liquor

- When every roster row has answered (yes, maybe, or declined), the roster card gets an animated rainbow border in the same colors as a yes name (`#roster-card.all-rsvped` in `index.html`, toggled by `everyoneRsvped()` in `app.js`). A person with no `first_signed_in_at`, `maybe_at`, or `declined_at` is still pending, and the border stays the normal frost line. Under reduced motion the border still cycles, more slowly.
- `secret_liq.py` is gitignored and run locally after that. It signs in as the operator's Supabase user (credentials in `.env`, or a prompt). It does not use the service role key. It stops if anyone is still pending. It loads yes RSVPs through `list_yes_rsvps()` (admin only), writes gitignored `secret_liquor_emails.txt` mapping display names to the addresses in `invite.py`, and draws targets.
- Matching follows `../secret-santa/secret_santa.py`: each person gives once and receives once, nobody is their own target, random retries when the draw gets stuck. Previous-year exclusions are not used. An odd yes count peels off one random trio first. That trio is a 3-cycle: each member gives to the person who is not giving to them. Everyone else is a normal draw.
- `DRY_RUN` defaults to True (print the draw, send nothing, do not write account targets). A real run emails each yes person their target, then calls `set_secret_liquor` so `/account` shows that target. Gitignored `secret_liquor_pairings.txt` is reused until `REMATCH` is set, so a second run does not reshuffle. Gitignored `secret_liquor_sent.txt` records who was already emailed.

## Security model (audited 2026-10-09)

- **Database privileges:** `anon` has NO privileges on any public table or function. `authenticated` has SELECT only on `cars`, `car_passengers`, `itinerary_days`, and on `people` only the columns `id, display_name, group_label, sort_order, first_signed_in_at, declined_at` (`user_id`, `slug`, and `is_admin` are hidden; `select=*` on people is denied by design, so always list columns). `profiles`/`user_logs`: per-row RLS on `auth.uid()`, `authenticated` can UPDATE only `profiles.display_name`; no TRUNCATE/REFERENCES/TRIGGER anywhere. `potential_drivers`, `secret_liquor`, and `login_emails` have no grants for `anon` or `authenticated`. Default privileges for new public objects are revoked for API roles (new tables need explicit grants + policies).
- **Functions:** `mark_first_sign_in`, `accept_invite`, `decline_invite`, `maybe_invite`, and `offer_to_drive` are `authenticated`-only and only touch the caller's own row (`offer_to_drive` inserts that row's id into `potential_drivers`). `mark_first_sign_in` also sets that same user's Auth email from `login_emails` when a row exists. `list_potential_drivers` is `authenticated`-only and returns names only when that caller's row has `is_admin`. `my_secret_liquor` is `authenticated`-only and returns only the caller's target name. `list_yes_rsvps` and `set_secret_liquor` are `authenticated`-only and raise `not allowed` unless that caller's row has `is_admin`. `admin_set_login_email` is `service_role`-only. `rls_auto_enable` (event trigger) and `handle_new_user` (auth trigger) have no API execute rights (verified auto-RLS on new tables still works). Remaining advisor WARNs for the caller-scoped RPCs are intentional.
- **Front end:** no `innerHTML`/`eval`; all DB text rendered with `textContent`. Link params (`e`,`k`,`a`) are length-checked, only used as credentials, and `a` is whitelisted. Password inputs `maxlength=72`. Each page has a strict CSP meta (`script-src 'self'`, `connect-src 'self'` + the Supabase origin, no inline scripts, `form-action 'none'`, `base-uri 'none'`) and `no-referrer`. Pages hide themselves if framed (clickjacking; GitHub Pages cannot send headers).
- **Supply chain:** supabase-js is vendored at `vendor/supabase-js-2.117.3.umd.js` (sha256 `d6a5c441...54a3`), no CDN code at runtime. To upgrade: `npm pack @supabase/supabase-js`, copy `dist/umd/supabase.js`, rename, update the 3 `<script>` tags.
- **Cache busting:** GitHub Pages caches ~10 min; script/CSS URLs carry `?v=10`, except `index.html` loads `app.js?v=15`, `account/index.html` loads `account.js?v=17`, `login.html` loads `login.js?v=14`, and `invite.html` loads `invite.js?v=12` (and `supabaseClient.js?v=7` in imports). Bump the number in all HTML/JS files whenever JS/CSS changes, or visitors can get stale files that conflict with the CSP.
- **Verified by live attack script (45 checks, all pass):** anon cannot read/write anything or call any RPC, sign-ups blocked (`signup_disabled`), admin API 401/403; a signed-in user cannot write trip data, read hidden columns, read/modify/delete/forge another user's rows, call admin or internal functions, or affect another person's decline state.
- **Secrets:** the repo and git history contain no passwords, JWTs, or service keys EXCEPT the original (now rotated and dead) Bringing passphrase committed on 2026-10-12; `.env`, `invite.py`, `secret_liq.py`, `secret_liquor_emails.txt`, `secret_liquor_pairings.txt`, `secret_liquor_sent.txt`, `invites.local.json`, the PDF, the local Batman GIF, and `__pycache__` are gitignored and were never committed. Importing `invite.py` writes bytecode that contains the address list, so the cache must stay untracked. `secret_liq.py` loads that list at runtime, so its cache must stay untracked too.

## Key design decisions

- Plain static HTML, no bundler; supabase-js via `https://esm.sh`. Publishable key committed deliberately (public by design; RLS protects data).
- Personal-link auth uses password sign-in with a per-person random key in the URL fragment (never sent to servers, stripped on load). Link carries the login email so switching to real emails needs no code change.
- No registration UI; accounts are admin-provisioned.
- Roster/trip content is data, not code. Group headings come from `group_label`.
- No emoji anywhere in the UI. ASCII penguin kept in the hero (`<`/`>` escaped in `<pre>`); keep it mirror-symmetric when editing (23-char width, center column 11).
- All paths relative for the `/Massanutten/` subpath.
- MCP safety: before any write, confirm via `get_project_url` + a schema fingerprint. Use the plugin namespace with explicit `project_id`; `user-supabase` may still point at EquityHealthSys until MCP reloads.

## Known limitations

- **Password strength:** the minimum is 6 characters; short passwords are still guessable if someone knows a person's email, despite Supabase's rate limits. Consider a longer minimum or enabling leaked-password protection.
- A signed-in user can change their OWN login email via the Auth API (`updateUser`); it only affects their own account. The same call changes only their own password. Leaked-password protection is off (Dashboard setting). The account page cannot display the current password.
- Signed-in users can see all roster names, who has signed in/declined, and the itinerary (by design). `cars` is still selectable but empty; `car_passengers` is still selectable. `profiles`/`user_logs` are unused by the UI and could be dropped.
- **Manual step:** Auth Site URL / redirect URLs (Dashboard > Authentication > URL Configuration): Site URL `https://massanuttennewyears.github.io/Massanutten/`, redirect `https://massanuttennewyears.github.io/Massanutten/**`.
- Personal links are bearer credentials; anyone with the link can sign in as that person until they set their own password (old key stops working after that) or the key is rotated.
- John's name only lights up on his next sign-in (his earlier logins predate `mark_first_sign_in`).
- PDF text kept verbatim (e.g. "Hrdy", "Will Smuth", "emploids", "booling", "Sendy"). The old Day 2 vs Day 3 split was replaced on 2026-10-14 by a 4-day trip starting Thu Dec 31.
- If `invites.local.json` is lost, keys cannot be recovered; rotate by setting new bcrypt hashes.
- Global `~/.cursor/mcp.json` `supabase` entry points at EquityHealthSys (`fkgwjkcixpjxxnhlqwow`) and is intentionally left as-is; this repo and `~/Desktop/dev/deploy/equityhealthsystems` each pin their project in `.cursor/mcp.json`.
- Pre-existing `public.rls_auto_enable()` (Supabase-provided) and "leaked password protection disabled" advisor warnings; left untouched.
- Auth gate is client-side only (static hosting): the page is hidden until verified, but data protection still rests on RLS. Because sessions use sessionStorage, each new tab/window needs a fresh sign-in (personal links sign in automatically); the 8h cap is a client-side check a determined user could bypass, and server-side limits (Dashboard session time-box/inactivity, Pro plan) are not set.
- The personal-link success path has been verified via the Auth API, not by clicking a real link in a browser (to keep keys out of logs).
- `potential_drivers` is only a list of people who clicked Yes on "Can you drive?". The account page shows that list when `list_potential_drivers()` succeeds. Clicking No does not remove a row that Yes already added.
